# 2026-11-04: MVP Day 1 (foundations + resource map)

**Done:** `uv` project (Python 3.12, src layout), ruff + mypy strict + pytest/Hypothesis config, GitHub Actions CI (lint/type on Ubuntu; tests on Ubuntu + macOS), `Clock`/`RealClock`/`FakeClock`, API models (`ObjectMeta`, `Node`, `Pod`, `Deployment`), the generic resource map and the extended-resource rule (X-1/X-2), quantity parsing, architecture lint (pure `chronos.core`, no `gpu` literal in `src/`), stub entry points.

**Bug caught by a round-trip test:** quantities were serialized as bare integers, but a bare `2000` for `cpu` parses back as 2000 *cores*, not 2000 millicores. Fix: `ResourceMap` serializes canonical strings (`"2"`, `"8Gi"`, `"3"`). Lesson: an internal unit (millicores) must never leak into a format that's parsed with a different default unit.

**Surprised by:** `ruff format .` also formats Python code blocks inside Markdown, which reflowed the hand-aligned pseudocode in the ADRs. Reverted, and `docs/` is now excluded from ruff.

**Nightly profile (20 000 examples) failed twice, both test-harness problems:** a `from_regex(...).filter(...)` name strategy inside `dictionaries()` raised `FlakyStrategyDefinition` (Hypothesis couldn't replay its draws), and the 60 s per-test timeout was too short. Fixed with a composite name strategy and `make test-nightly` (`--timeout=0`). All 8 properties now pass at 20 000 examples.

**Deviation from the plan:** M1.6 said to accept ADR-0001–0004 and 0006. Accepted 0001, 0002 and 0006 only. ADR-0003 waits for pre-commit and the Makefile targets it lists (pre-commit is P0.3 in PM-1), and ADR-0004 waits for the FastAPI server (Day 3), since "Accepted" means implemented.

# 2026-11-04: MVP Day 2 (versioned store)

**Done:** `chronos.store`: one global revision, CAS on `resource_version` for update / update_status / delete / bind, deep copies in and out, a `pods_on(node)` index, and `bind()` re-checking capacity for every resource name (missing name = 0). Validation: `uid` and `owner` immutable, bind-once `node_name`, `generation` bumps only on spec change, pods are created Pending and unbound. Tests: unit tests for every error path, a Hypothesis `RuleBasedStateMachine` against a dict + counter model (S1, S5), and a bind property over random resource-name sets (S2, S11). Stateful test green at the `ci` profile.

**Bug caught by the unit tests:** free capacity was computed as `capacity − (capacity + allocated)`, so every bind failed with `InsufficientCapacity`. Fixed with `sub(capacity, allocated)`.

**Mutation check:** removing the CAS check, the bind-once check or the capacity check each makes a property test fail.

**Decisions not spelled out in the plan:**
- Terminal pod phases (Succeeded/Failed) are final. A terminal pod's resources are already free for other binds, so letting it come back to Running could overcommit the node (S2).
- A node's capacity can't be lowered below what's allocated on it.
- `node.status.allocated` is computed on every read, never stored. That's part of M5.3, done early because `bind()` needs it.
- Binding doesn't bump `generation`: it's a system write, not a user spec change.

# 2026-11-04: MVP Day 3 (API, clients, heartbeats, node health)

**Done:** FastAPI server (`chronosd run`) with CRUD, status, binding, register and heartbeat routes; store errors map to 404/409/422 with a `reason` and `details` the HTTP client uses to raise the same exception. `StoreClient` protocol with `LocalStoreClient` and `HttpStoreClient` (explicit timeouts; transport errors raise `Unavailable`). In-memory heartbeat leases on the server's monotonic clock; `core/node_health.condition()`; node lifecycle controller (250 ms tick, CAS on transitions only). Tests: node-health boundary table, one contract suite run against both clients (HTTP through `httpx.ASGITransport`), HTTP status codes, lifecycle on a FakeClock. End-of-step check done with `curl` against a real `chronosd`.

**Bug caught by the contract suite:** `register()` takes capacity in internal units (cpu in millicores). Building a model from that map re-parsed a bare `4000` as 4000 *cores*, on the HTTP path and on the local client's create path. Same root cause as Day 1's round-trip bug: an internal int must never go back through the parser. Fix: hand models canonical strings (`format_resources`). Lesson: running one suite against both clients paid off on its first run.

**Decisions not spelled out in the plan:**
- A `register` endpoint (not in PLAN.md §4.4) creates the node or adopts it for a new agent epoch. Recorded in ADR-0004.
- Going NotReady revokes the node's `agent_epoch`. The old incarnation's heartbeats then get 409, so NotReady → Ready only happens through re-registration, as the state machine in PLAN.md §4.3 says.
- A node first seen without a heartbeat (e.g. created with `curl`) starts its lease when the controller first sees it, so it gets a full grace period.
- No lock around the store: route handlers are `async def`, so they run one at a time on the event loop. A lock arrives with the WAL (PM-2), when writes start to await.

**ADR-0004 → Accepted**, noting that `watch` lands in PM-3.

# 2026-11-04: MVP Day 4 (agent + real processes)

**Done:** `chronos-agent run --name --cpu --mem --resource name=qty --server --data-dir`: registers under a fresh epoch, runs a heartbeat loop and a sync loop as separate tasks (a slow stop never delays a heartbeat), re-registers on `EpochMismatch`/`NotFound`, and stops its workloads on SIGTERM/SIGINT. `ProcessRuntime`: each pod runs in its own session (pid == pgid), with `CHRONOS_POD_UID/NAME/NODE` in its env, per-pod stdout/stderr logs, and pidfiles (`agent.pid`, `pids/<uid>`). Stopping sends SIGTERM to the group, then SIGKILL after the grace period. A command that can't start becomes exit code 127. `core/agent_sync.plan()` (pure): start desired pods with no process, stop running processes nobody wants, forget exited ones, report status diffs (CAS against the version read). `testing/workload.py`, `testing/cluster.py` (real `chronosd` + agents on free ports, `kill_node()`, `eventually()`, teardown that fails the test if any pod process group is still alive).

**Tests:** unit tests per `agent_sync` rule. Properties: converges within three rounds and then plans nothing; never stops a desired pod; stops exactly the running processes nobody wants. Integration (9 tests, about 16 s): 3 agents go Ready with the right capacity; a bound pod becomes a real process whose log shows its pod and node; deleting the pod stops the process; a SIGTERM-ignoring workload is still alive at grace/2 and SIGKILLed after the grace period; a non-zero exit gives `Failed(Exited, 3)`; a bad command gives exit code 127; `kill_node` gives Unknown and then NotReady inside the configured windows (L1); a restarted agent gets a new epoch; a graceful agent stop stops its workloads. Passed 3× in a row and once with `-n 4`; `pgrep` shows no leftover processes afterwards.

**Bug caught by `filterwarnings = error`:** the cluster helper left each log file handle open after `Popen` (the child has its own copy). That raised a ResourceWarning, which the suite treats as an error.

**Decisions not spelled out in the plan:**
- Pods are keyed by uid, not name, so a pod recreated under the same name never adopts the old process.
- Reporting a workload's exit as `Failed(Exited, code)` (M6.4) landed today, because the sync loop has to do something with an exited process. Exit 0 under `Never`/`OnFailure` becomes `Succeeded`. M6.4 is ticked on Day 6 with its end-to-end test.
- `ready = True` while a pod is Running (there are no probes until Tier 2).
- After a stop, the runtime sends a last SIGKILL to the group even if the leader already exited, to catch leftover children. If the pgid were reused in that instant, an unrelated group could be hit; this goes away once the shim is the group leader (PM-1).

# 2026-11-04: MVP Day 5 (scheduler + extended-resource hard constraint)

**Done:** `core/schedule.py`: filter/score plugins behind a registry (`register_filter`, `register_score`; a duplicate name is an error), `SchedulerConfig` (enabled filters, score weights) resolved into a `Profile` (unknown name or negative weight is a `ConfigError`), built-ins `NodeReady`, `NodeSchedulable`, `FitsResources` (iterates over resource names, missing name = 0) and `LeastAllocated`, all registered through the same calls. `pick_node` breaks ties by node name and aggregates reasons (`0/3 nodes available: Insufficient chronos.dev/slot (2/3 nodes), node NotReady (1/3 nodes)`). `SchedulerController` (250 ms, oldest pod first, authoritative reads; a failed bind is retried next tick; the Unschedulable status is written only when its message changes) runs inside `chronosd`. `node.status.allocated` now has the same keys as capacity (zeros included). `bind()` clears a stale reason and message.

**Tests:** unit tests per plugin, a `FitsResources` table (including nodes lacking the resource and zero requests), and registry config errors. Properties over random clusters and random extended-resource names (every name missing from at least one node): no node overcommitted (S2); extended resources are a hard constraint (S11); every pod left pending fits nowhere and says why; deterministic placement; a single pod that fits somewhere is placed (L3); ticks reach a fixed point. **Early PX.9:** `example.com/widget` plus a test-only `test.FewestWidgetsLeft` score plugin, registered from test code, pass the scheduling and bind properties, and the plugin changes placement. The diff touches no production code for them. Integration: two slot pods on `plain-1` + `slot-a` give one Running on `slot-a` and one `Unschedulable (Insufficient chronos.dev/slot (2/2 nodes))`; deleting the first lets the second take the slot, never `plain-1`.

**End-of-step check:** S2/S11 scheduling, bind and widget properties at the `nightly` profile (20 000 examples each): 9 passed in 5 min 47 s (`-n 4`).

**Mutation check:** making `FitsResources` ignore extended resources, making `NodeReady` accept every node, or removing the extended-resource check from both the filter and the store's bind each fails a property. A tie-break that depends on input order isn't caught by the properties (the store always lists nodes sorted by name); the unit test that shuffles nodes catches it.

**Caught along the way:**
- The first "second tick writes nothing" property was wrong, not the scheduler. A pending pod's honest reason changes when another pod is bound in the same tick, so one rewrite is correct. It's now a fixed-point property: the third tick writes nothing.
- The store's stateful model test failed on the deliberate change that `bind()` clears the message. The model was updated, which is the kind of change it's there to flag.
- The Day 4 integration tests bound pods by hand, which would race the scheduler. They now let the scheduler place pods.
