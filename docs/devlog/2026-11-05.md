## Part 2: shim + self-fencing (ADR-0012)
**Done:** every pod runs under `python -m chronos.shim` (also a `chronos-shim` script), which leads the pod's process group with the workload as its child. The agent keeps `last_ok_send`, the **send** time of its last accepted heartbeat, and writes it atomically to `<data-dir>/lease`. Three agent loops: heartbeat, fence watch (on its own, because the heartbeat loop can sit in a register retry while the server is down) and sync (which checks the fence before starting anything). Fenced mode stops every workload, starts and reports nothing, and is left only after an accepted heartbeat. Stops caused by fencing are recorded as `FENCED_EXIT_CODE`, so those pods are started again rather than failed. The shim polls the lease every 100 ms: older than F → SIGTERM the group, then SIGKILL after K; older than E → SIGKILL at once; a missing or unreadable lease counts as infinitely old. Registration sends the agent's F, K and drift; the server refuses them unless F + K + drift < E and returns E for the shims. The agent refuses F ≤ 3 heartbeats and `shim_poll ≥ K` at startup. Test timings: F 1.0 + K 0.5 + drift 0.2 = 1.7 < E 2.0. Demo: 2 + 1 + 1 = 4 < 5.

**Tests:**
- Unit boundary tables for `should_fence`, `shim_action` and the inequality, plus agent config validation.
- Agent unit tests on a FakeClock: lease = send time under a 3 s slow reply; fences at F + ε (not at F) and stops only running workloads; starts nothing while fenced; a success unfences.
- Real shim processes: exit code and signal passed through, stale lease → graceful fence (exit 86), SIGTERM-ignoring workload SIGKILLed after K, lease past E → SIGKILL in under 0.5 s, missing lease → SIGKILL, the agent's own SIGTERM, 127 for a bad command.
- Integration, sampling live process groups every 20 ms: **paused agent** (SIGSTOP) → the workload is dead within F + K + 0.5 s and the replica count is never exceeded; **agent killed** (`kill -9`) → the shim fences it and the count is never exceeded; **whole-node freeze** (agent + shims + workloads SIGSTOPped until the replacement runs, then only the pods resumed) → a SIGTERM-ignoring stale workload dies about 65 ms after resume; **a short agent pause** (F/2) doesn't fence.
- Server refusal checked by hand: `fence_timeout + termination_grace + drift_margin = 6s must be < eviction_timeout = 5s, ...`.

**Mutation checks:** making the shim ignore the lease fails the agent-crash and freeze tests. Dropping the immediate SIGKILL past E fails the freeze test (0.55 s against a 0.3 s bound; the real path takes about 65 ms). Measuring from ack time instead of send time fails the agent unit test.

**Caught along the way:**
- `signal.signal(SIGKILL, ...)` raises, so the shim's "die the way the workload died" path now skips setting a handler for SIGKILL/SIGSTOP.
- Two shim tests timed from after the shim booted (about 0.25 s of Python startup) instead of from the lease write.
- The first freeze test waited for "store matches the live process set", which can't happen while the old workload is frozen. It failed before resuming, so teardown hung on stopped processes and left some behind. Teardown now SIGCONTs everything first and SIGKILLs agents that don't stop.
- With the whole node resuming, the agent itself also stops the stale workload fast enough, so the freeze test proved nothing about the shim. It now resumes only the pods and uses a workload that ignores SIGTERM.

**Changed:** a pod's `status.pid` is now its process group (the shim's pid); the integration helpers compare process groups.

## Part 3: orphan cleanup (P2.7)
**Done:** before registering, the agent kills the pod process groups its predecessor left in `pids/`. A pidfile is trusted only if `psutil` shows that process is still a `chronos.shim` with that pod uid on its command line, so a reused PID never gets an unrelated process killed. Every pidfile is removed either way. New dependency: `psutil` (already planned for the chaos checker, ADR-0003).

**Tests:** on real processes, an orphaned shim is SIGKILLed while an unrelated live process listed under a reused PID survives, and dead or garbage pidfiles are removed. Integration: `kill -9` the agent and restart it at once (before its shims would fence): the old workloads are killed before new ones start (live groups sampled every 20 ms never exceed 2), and the pods come back with new process groups.

**Mutation check:** with the cleanup removed, the restart test fails.

**Caught along the way:** the first version of the restart test passed vacuously at first and then failed, because right after the restart the store still listed the old, still-alive processes, so "2 Running and matching the OS" was already true. It now waits for the pods to report new process groups.

## Part 4: restart in place with backoff (P2.6)
**Done:** `core/agent_sync.plan(node, pods, procs, now, backoff)`: when a desired pod's process exits, `Always` restarts it on any exit, `OnFailure` on a non-zero exit, and `Never` reports it as final (`Succeeded` for 0, `Failed(Exited)` otherwise). Restarts wait `base · 2^(n-1)` (capped) over *consecutive* crashes n; a run of at least `reset_after` resets n. While waiting, the pod is `Running` with `reason=CrashLoopBackOff`, `ready=false`, the last exit code and `back-off Ns before restarting`. `restart_count` comes from the agent (the stored value on the first start, +1 per restart). `LocalProc` gained `started_at`, `exited_at`, `restarts` and `crashes`. The runtime takes an injected clock. Agent flags `--crash-backoff-base/cap/reset` (defaults 1 s, 10 s, 60 s; tests 0.2 s and 1.6 s). A crash-looping pod still counts as active, so the deployment no longer churns pods (A.8 #6).

**Tests:** unit tests for the waiting status (and that it isn't rewritten each tick), restart once the delay has passed, delays of 1, 2, 4, 8, 8, 8 s, reset after a stable run, OnFailure with clean vs failing exits, restart counts. Integration: a crashing `Always` workload stays **one pod** with restart counts 1, 2, 3, 4 at growing intervals and shows `CrashLoopBackOff`; a `Never` workload is `Failed(Exited, 3)` and replaced. The agent_sync convergence properties still pass unchanged.

**Mutation check:** a constant delay fails both the unit "doubling" test and the integration "growing intervals" test.

**Changed on purpose:** the MVP rule "a crash with `Always` → Failed → replacement pod" is gone. Day 4's exit-reporting tests now use `restartPolicy: Never`, which is what they test.

## Part 5: two-phase pod deletion (P4.7)
**Done:** deleting a bound, unfinished pod sets `deletion_timestamp` (one revision bump, and a repeat delete is a no-op); its spec is frozen, its status can still be written, it can't be bound, and its resources stay allocated. Unbound or finished pods, other kinds, and `force=true` are removed at once. The agent stops a terminating pod's process and, once nothing runs for it, sends `DELETE ...?force=true` with the version it read (`Finalize` in `agent_sync`). `chronosctl get pods` shows `Terminating`. The deployment controller's finished-pod GC now counts only Succeeded/Failed pods (terminating pods are neither active nor finished).

**Tests:** store unit tests (marked not removed, idempotent, spec frozen but status writable, force frees resources, unbound and finished pods go at once, a terminating pod can't be bound). The stateful model test now models two-phase delete and force; it passes at 1 000 examples. agent_sync: stop-not-finalize while running, finalize once gone, another node's pods left alone; a new property that it never finalizes a pod whose process still runs. Integration: a SIGTERM-ignoring workload's pod stays visible through the grace period and leaves the API only after its process is dead (sampled every 20 ms).

**Mutation check:** letting the agent finalize while the process still runs fails both the new property and the integration test.

**Linux, found while waiting for CI:** the Docker run copied the repo with macOS `tar`, which adds AppleDouble `._*` files, and ruff failed on 79 of them before any test ran. Fixed with `COPYFILE_DISABLE=1`, also in `scripts/fresh-clone-check.sh`.

## Part 6: workload types and resource providers (X-4, X-5)
**Done:**
- **X-4** `chronos/api/workload_types.py`: `WorkloadType` protocol (`validate(template)`, `prepare(pod) -> (argv, env)`), `register_workload_type` (a duplicate is an error), and `generic` registered through the same call. `PodTemplate.workload_type` (default `generic`) is checked when the template is parsed, so an unknown type is a 422 from the API, an error from `chronosctl apply`, and a type can veto a template. The runtime runs whatever `prepare` returns and never branches on the type.
- **X-5** `chronos/agent/providers.py`: `ResourceProvider` protocol (`allocate(uid, n)`, `release(uid)`, `env(units)`), factories registered per resource name, and a `CountingProvider` (lowest free units "0".."n-1") for any advertised extended resource without its own. `Providers.allocate` is all-or-nothing, and on failure releases only what that call took. The runtime allocates before spawning (merging the provider's env in) and releases when the process exits. Units are in `LocalProc.assigned` and `pod.status.assigned` while running, and cleared on exit. If a node can't supply the units, the agent reports `Failed(ProviderError)` and starts nothing.

**Tests:** registry rules, unknown type → ValidationError and HTTP 422, a test type vetoing a template; counting provider behaviour, all-or-nothing, not freeing units a pod already held, no units for cpu/memory or zero requests, an unadvertised resource. **S12 property:** random allocate/release sequences against a model never give one unit to two live pods, and releasing everything restores full capacity. **Seams from test code only:** a fake workload type and a fake `example.com/widget` provider run a real process through the unchanged runtime, which prints the widget ids and the type's env var, and the units are released afterwards. Integration: a running slot pod reports `assigned: {chronos.dev/slot: ["0"]}`; on a 2-slot node two pods get "0" and "1", and after one is deleted the next pod gets its unit.

**Mutation check:** a counting provider that doesn't take units off the free list fails the S12 property and both integration tests.

**Deviations from ADR-0023 (recorded there in part 7):**
- The WorkloadType registry is in `chronos/api/`, not `chronos/agent/`, because templates are validated wherever they're parsed (server, CLI, agent).
- Providers are keyed by pod uid rather than taking the pod, because release happens when the process exits, when only the uid is at hand.
- Providers register as factories `(resource, capacity) -> provider`, because a provider needs the node's capacity, which isn't known at import time.

**Caught along the way:** the architecture lint flagged a docstring mentioning a Stage 2 GPU provider; reworded.

## Part 7: partition test, README, ADRs, exit
**Partition:** S3/S4 under network partition needed a test before PM-1 could exit. A minimal cuttable TCP forwarder in `tests/integration/proxy.py` sits between one agent and `chronosd` (the full fault proxy is PM-6). Cutting it: the agent fences, the workload is dead within F + K + 0.5 s, the replacement starts on the other node only after eviction, and live groups never exceed 2. Healing it doesn't resurrect the evicted pod. The first version deadlocked: on Python 3.12, `Server.wait_closed()` waits for every open connection, and `cut()` closed the connections after waiting; it now closes them first.
