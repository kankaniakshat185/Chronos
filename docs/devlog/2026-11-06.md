# 2026-11-06: PM-2 (durability)

**Done:**
- `store/codec.py`: `[u32 length][u32 crc32][JSON {rev, op, kind, name, object}]`, little-endian; a frame decodes completely or is invalid.
- `store/wal.py`: segments `wal-<first rev>.log` (rotation, directory fsync); `durable_sync` (`F_FULLFSYNC` on macOS, fsync elsewhere); snapshots written as tmp → sync → rename → directory sync, keeping the newest two and deleting segments older than the older one.
- `recover()`: the newest snapshot with a valid CRC (falling back to the previous one), then contiguous records. An invalid frame at the end of the last segment with nothing intact after it is a torn write and is truncated; any other damage, or a revision gap, refuses to start. `repair=False` only reports.
- `common/crashpoint.py`: `CHRONOS_CRASHPOINT=<name>[:<nth>]` exits with 137. Points: `wal.before_write`, `wal.torn_write` (writes half a frame, then exits), `wal.before_fsync`, `wal.after_fsync_before_apply`, `segment.rotate`, `snapshot.before_rename`, `snapshot.after_rename_before_dirsync`.
- Store: every write goes through one path, log first and then `_apply_put`/`_apply_delete`, which recovery replays too. The pod-to-node index is maintained only inside apply, where before it was updated before the commit. A failed append raises `Unavailable` with memory untouched. `Store.open(data_dir)`.
- `chronosd run --data-dir` (default `~/.chronos/server`), `--no-wal-sync` (benchmarks only, warns loudly), `--snapshot-every`; it refuses to start on a corrupt log (exit 3). `chronosd wal-verify DIR`. Test clusters and the demo get their own server data dir; `restart_server()` keeps it.

**Not done here:** group commit (P6.2, optional in the plan) moved to PM-6, where benchmark B5 decides whether it's needed. A full fsync costs about 3 ms per write on this Mac (p50 2.97 ms, p99 3.44 ms), which is fine for one synchronous writer at Stage 1's scale.

**Tests:**
- Codec round trip.
- Recovery from **every byte truncation offset** of a 6-record log equals exactly the complete-record prefix, with the torn bytes removed.
- A bit flip in the last record is truncated; a bit flip anywhere before it refuses to start (100 random positions).
- A revision gap refuses to start; a failed log write (disk full) changes nothing.
- Reopening gives back exactly the same state after random writes with random snapshot intervals, and revisions continue from there (U2.3). Old segments are pruned; a damaged newest snapshot falls back; a leftover `.tmp` is ignored.
- **Durability harness (S8):** a seeded writer subprocess crashes at the nth hit of a crash point, where n is drawn from a crash-free calibration run of that seed, so every case really crashes. The recovered state must equal a reference run's state after the last finished write or after the in-flight one, and nothing else. **7 points × 50 seeds = 350 cases pass** (39 s with `-n auto`).
- **Control-plane restarts (U2.2, L4):** (a) `kill -9 chronosd` and back within F (3 s here): the same pods, PIDs and revision, no fencing, nodes still Ready past E. (b) Down longer than F: zero workload processes, then after the restart the same pods restart on their own nodes with new PIDs and nothing becomes NodeLost (startup grace, U2.1). ## Group commit (P6.2), built after all
At first deferred (optional in the plan); you asked for it now.

**Design:**
- The WAL gets three sync modes: `full` (sync per write), `group` (append now, `flush()` syncs) and `none` (benchmarks only).
- In `group` mode a write is applied to memory at once, but `LocalStoreClient` answers *nothing* (reads, writes, heartbeats, registrations, **and errors**) until `store.durable_revision` covers the revision it saw. The first waiter starts a `--group-window` timer (2 ms) and one sync releases everyone. So no client and no in-process controller acts on state a crash could take back, and since the log is in order a crash keeps a prefix of the unacknowledged batch.
- Rotating a segment and closing both flush first.
- A failed group sync exits the process (code 70), because retrying an fsync after a failure can report success for pages the kernel already dropped (the PostgreSQL "fsyncgate" lesson), so recovery from the log decides.

**Tests:**
- 20 concurrent writes take ≤ 2 syncs (full mode: one per write).
- A read and an `AlreadyExists` error caused by a pending write are answered only after the sync.
- Reopening keeps everything acknowledged.
- **Sync accounting**: every acknowledgement comes after an fsync whose file size covers that write's record.
- The crash harness runs in both modes. In group mode the writer acknowledges only after `flush()`, and the recovered state may be any state from the last acknowledged one through the end of the in-flight batch. **7 points × 50 seeds × 2 modes = 700 cases pass.**

**Mutation checks:**
- Answering before the sync → 2 tests fail.
- **A flush that skips the fsync passed all 56 crash/WAL/group tests**, because a process crash keeps the page cache, so no crash test can tell "written" from "synced". The sync-accounting test was added for exactly that, and it now catches both "never syncs" mutations (group and full).

**Early B5** (`bench/b5_wal_sync.py`, this Mac, one run):

| writers | mode | writes/s | p50 ms | p99 ms |
|---|---|---|---|---|
| 32 | full | 275 | 3.33 | 10.34 |
| 32 | group | 2 906 | 10.48 | 18.99 |
| 32 | none | 7 832 | 0.12 | 0.18 |
| 1 | full | 265 | 3.43 | 9.41 |
| 1 | group | 163 | 5.98 | 10.28 |

Group commit buys about 10× the throughput under concurrency at the cost of latency, and is slower for a single writer (nothing to share the sync with, plus the window). `full` stays the default.

## PM-3: watch, informers, work queue, expectations, assume cache, kind registry

Polling is gone. Controllers in `chronosd` and the agents now learn about changes from a long-poll watch on the store's revision log, keep local caches, and reconcile one key at a time.

**What was built:**
- **Watch log** (`store/watchlog.py`): the last 10 000 events in a ring. Every write produces exactly one event and bumps the revision by one, so the event for revision r is in slot `(r − 1) % N` with no search. Anything older than the oldest retained event is refused with `Compacted` (HTTP 410): the client relists. A watch never gets a partial history. After a restart the log starts empty at the recovered revision, so every watcher from before relists.
- **Watch endpoint**: `GET /api/v1/watch/{plural}?since=&timeout=&node=` for every kind; `StoreClient.watch()` on both clients. The `node=` filter matches the old *or* the new version of an object, so a watcher for unbound pods sees a pod leave when it's bound. In-process watches wait for the durable revision like every other read, so group commit never delivers an event a crash could take back.
- **Controller runtime** (`controllers/runtime.py`): `Informer` (list, watch, relist on 410; handlers get `(old, new)`; a relist reports exactly the difference), shared `Informers` (one per kind), `WorkQueue` (dedup, one in-flight per key, requeue if changed while processing, per-key backoff), `Expectations`, a `Controller` base with a 30 s resync, and the controller registry.
- **Deployment controller** on informers, with **expectations**. Its keys are deployment uids (what pods carry as `owner`). Orphan GC confirms the owner is gone with a live read first.
- **Scheduler** on informers, with the **assume cache**. Allocation is summed from the pod cache by a handler; an assumed bind counts until the cache shows the pod bound. Any node change, or freed capacity, requeues the pending pods.
- **Node lifecycle** on informers. It resyncs every 250 ms (heartbeat silence grows with no event) and confirms NotReady with a live read before evicting.
- **Agent** watches `pods?node=self` and syncs on every cache change, every local process start or exit, and at least every `--resync-interval` (1 s; crash-loop backoffs expire with no event). `--poll-interval` is gone.
- **Kind registry (X-6)**: `store/kinds.py`; every kind subclasses `ApiObject`; the store, routes, clients, manifest loader and CLI are generic. `chronosd` builds whatever controllers are registered.

**Regression gate:** the 36 MVP integration tests pass on the new runtime. The pure-core property tests are untouched; the shell tests only changed `tick()` to `run_once()`. Two integration tests needed one line each (below).

**What broke, and why:**
1. *chronosd took more than 10 s to stop.* Uvicorn's graceful shutdown waits for open requests, and every agent now holds a 30 s watch. First fix: a 1 s graceful timeout. That left a traceback per cancelled watch in the log, so the HTTP watch route now races the watch against a "closing" event set from the shutdown signal and answers with an empty batch (clients just watch again from the same revision).
2. *The first version of that shutdown fix hung chronosd for good.* I had made every watch return at once on shutdown, including the in-process informers' watches. An in-process watch that returns immediately never suspends, so those informers spun on the event loop and starved uvicorn's shutdown. The hung test servers were never killed, and about 30 of them sat at 20% CPU each (load average 180) until I found and killed them; that load also made a restart-timing test fail. Fixes: shutdown now only answers HTTP watches; and `Cluster.close()` SIGKILLs a chronosd that ignores SIGTERM for 10 s (and fails the test), so this can't leak again.
3. *A lost wakeup in the in-process watch.* `_next_change` wrapped `watch.wait()` in a task, and the task registered its waiter only when first scheduled. A write that landed between "no events yet" and that moment woke nobody, so the watch slept until its 30 s timeout. The X-6 widget test hit it by creating an object right at startup. The fix registers the waiter synchronously, with no `await` between the check and the registration. A deterministic regression test puts the write exactly in that gap.
4. *A pod started by the agent was never reported Running.* Reporting needs a second sync after the start, and with polling gone nothing triggered it. The runtime now calls `on_change` on every start and exit (and on "couldn't start"). Found by `test_watch.py`, which runs the agent with a 30 s resync.
5. *Two MVP integration tests started failing:* the SIGTERM-ignoring workload died from SIGTERM. Running is now reported the moment the process starts (polling used to add ≥ 100 ms), so the tests deleted the pod before the Python workload had installed its `SIG_IGN` handler. The product is right (Running = process started; there are no readiness probes yet), and the tests now wait for the workload's first output line, which it prints after installing the handler.

**New tests:** the S6 replay property (from every revision of random histories, with compaction, for the whole kind, the node filter and small batches); watch contract tests on both clients; work queue, expectations, informer and restart-relist unit tests; the expectations and assume-cache stale-cache tests; the stale node cache eviction test; the node-event requeue test; `test_watch.py` (agent driven by the watch); `test_kind_registry.py` (X-6); the group-commit ordering test extended to watches.

**Mutation checks:** 15 for this block, logged in [testing-the-tests.md](../testing-the-tests.md) #26–#40. Every one is caught now. Three survived at first and each got a test: the informer ignoring 410 (the test relisted by itself), cached-condition eviction (nothing covered a stale node cache), and node-event requeue (only the big demo test noticed).

**Verified:** macOS 476 passed (`make check`), pre-commit clean, no leftover processes; Linux (Docker) 476 passed, ruff and mypy clean.

## PM-4: deterministic simulation, and the real bugs it found

`python -m chronos.sim --seed N` runs a whole cluster (the control plane and 2-6 agents) under virtual time and one seeded RNG, injects faults, and checks the invariants after every event.

**What is real, what is simulated:**
- Real: the `Store` with its WAL and recovery, `LocalStoreClient`, `Leases`, the three controllers on shared informers, the `Agent` (register, heartbeat, fence check, pod informer, `sync_once`), `Providers`, and the pure core.
- Simulated: time, the network (per-direction links with delay, drop, spikes and cuts), processes and their shims, and the disk's sync behaviour. The WAL writes real files, but fsync is recorded instead of performed, and a control-plane crash cuts every file back to its last synced size.
- How the async code runs without an event loop: in full-sync mode the control plane's coroutines never actually wait, so `run_sync()` drives them in one `send()`. The agent's coroutines run as sim `Task`s, which can only await sim futures (a network reply, a timer). Each control-plane step is one action chosen by the RNG: one informer catches up, or one controller handles one key. So caches are stale for random stretches, and interleavings differ per seed.
- Four production hooks made this possible, all dependency injection: the work queue keeps delayed keys in a heap instead of timer tasks; `Agent` takes `rng` and `new_epoch`; `Informer` takes `rng`; `DeploymentController` takes `new_name`.

**Faults:** node crash; agent crash; agent pause; whole-node freeze; partitions (one-way or both); delay spikes; message drops; "degrade" (slow, then dead); workload crash storms; control-plane crash with recovery from the truncated WAL. User actions: deploy, scale, undeploy. Every run invents 0-2 extended resource names and puts them on random nodes (X-7).

**Checks:**
- After every event: S1, S2, S3, S4, S5, S6 (an informer that says it's caught up must hold exactly the store's objects), S8 (on every restart, the recovered revision is at least the highest one ever acknowledged), S11, S12.
- After everything heals and 25 quiet seconds: L1, L2, L3, L5.
- Same seed, same trace: the trace's SHA-256 is compared across runs and across `PYTHONHASHSEED` values.

**Real bugs found** (all three fixed, each with a unit test and a regression seed):
1. **Seed 9 (S3), whole-node freeze.** After a thaw, the agent's heartbeat was refused (epoch revoked), it re-registered within milliseconds, and the reply **renewed the lease before the shim's next poll**. The shim then saw a fresh lease and let the replaced workload run, until the agent's graceful stop up to K later. That broke the README's "at most one shim poll" claim. Fix: the agent applies the shim's second rule itself. If its lease is older than E it SIGKILLs every workload at once, in every fence check and **before** writing a new lease.
2. **Seed 25 (S3), introduced by PM-3.** An agent paused across a control-plane restart re-registered, then **restarted pods from its stale pod cache** that the server had already evicted and replaced. Its in-flight watch had died with the old control plane and wouldn't time out for 15 s. The MVP agent couldn't do this, because it listed fresh on every poll. Fix: the agent remembers the revision of its registration (`reply.node.resource_version`) and acts only once its pod cache has reached it, listing if needed.
3. **Seed 21 (S6), introduced by my first fix for #2.** That fix relisted while the informer's own watch was in flight. The replies crossed, and an **older list wiped a pod the watch had just delivered**. Fix: the informer is now safe under concurrent use. A list older than the cache is dropped (unless a relist is due), and a watch batch that was in flight across a relist is dropped. The S6 check found this as a canary side effect: it appeared under `skip_bind_capacity_check`, a canary unrelated to watches, which is why it looked wrong.

**Bugs in the simulator itself:**
- A seed under `fence_after_eviction` hung a worker for good. With F > E, the new "past E → SIGKILL" rule killed a workload the unfenced agent then restarted, at the same virtual instant, forever. A simulated process start took zero time. Fixed by giving starts a 1-20 ms latency (fork + exec), and the engine now raises on livelock (100 000 events at one instant) or runaway (2 million events) instead of hanging.
- Agent logging went to stderr; it is now disabled during runs (the trace tells the story).

**Canaries:** all 10 are detected. Two needed the simulator, not the canary, to change:
- `watch_skip_on_compaction` was never detected with a 64-event history (agents rarely fell that far behind). The sim now uses 16.
- `measure_fence_from_ack_time` can't be detected **at all** in Chronos as built. The 0.4 s heartbeat timeout means no reply later than that is ever accepted, so ack time trails send time by less than E − F − K − poll = 1.4 s. The timeout alone masks the bug. The canary now removes both protections (as `skip_bind_capacity_check` also removes the assume cache), and a "degrade" fault was added.

**Speed:** about 1 s per seed on one core; 200 seeds in about 41 s on 8 workers.

## PM-5: CLI, events, structured logs, metrics, Prometheus + Grafana

**Built:**
- **CLI:** `get KIND [NAME] -o table|wide|yaml|json [--watch]` for any registered kind; `describe` (the object plus its events); `logs` (local mode, reads the agent's files); `cordon`/`uncordon`; `get events`. `--watch` uses the same long-poll watch as the agents and lists again after a 410. Drain stays in PM-9.
- **Events:** a new kind, registered through the X-6 registry like any other. One Event per (object, reason), repeats counted ("x14"). Emitted: Scheduled, FailedScheduling, NodeNotReady, Evicted, Started, BackOff, Fenced, and ProviderError via the pod's status. Recording is best effort and never fails the caller. "Fenced" is recorded when the agent leaves Fenced mode, since while fenced the control plane is unreachable by definition. An event GC controller deletes events not seen for an hour.
- **Logs:** `--log-format json` gives one object per line, with `component` plus context from `contextvars`: the agent's `node`, and each reconcile's `controller`, `key` and `trace_id`. I used the standard library rather than structlog (no new dependency for the same job).
- **Metrics:** the 14-metric catalog in `common/metrics.py`, golden-tested. Cluster-state gauges are computed from the store at scrape time; counters and histograms live in separate registries for `chronosd` and the agent. CPU is in cores. The agent serves its own `/metrics` port.
- **Stack:** `deploy/observability/` with pinned Prometheus and Grafana, 1 s scrapes, file service discovery written by the demo script and the test cluster, and a provisioned dashboard generated by a script; `make observability`.
- **`MostAllocated`**, selected with `chronosd --scheduler-policy pack`.
- **Examples:** `hello`, `crashy`, `big`.

**Tests:** metric-catalog golden; dashboard lint (catalog-only queries, every metric on a panel, JSON matches the generator); events (dedup and count, names, best effort, GC); JSON log lines with context; CLI (yaml/json, describe with events, cordon, logs, `--watch`); a real-process `/metrics` test; and the `observability-smoke` test. Locally against the real stack the smoke test passed: all 4 targets up, 3 Ready, NotReady seen after killing a node, the dashboard provisioned, every panel query valid PromQL. Also ran the demo by hand: events for the crash loop counted x3, `describe` on the oversized pod says "Insufficient cpu", `logs` prints the workload's line.

**Mutation checks:** 6, all caught after one test fix. GC by `first_seen` instead of `last_seen` survived: every test event had been recorded once, so the two were equal. The test now has an event that is old but still recurring. One `sed` produced a syntax error rather than a bug, so that "catch" didn't count and was redone (a reminder to check that a mutant even compiles).

## PM-6: chaos on real processes, and benchmarks

**Built:**
- **`testing/faultproxy.py`:** an asyncio TCP proxy per agent link, with modes pass / delay / drop / blackhole / reset, switchable at runtime (and over a tiny HTTP admin port when run on its own).
- **`python -m chronos.testing.chaos`:**
  - A real `chronosd` plus N agents, each agent through its own proxy.
  - Faults: kill -9 of an agent, a whole node, or `chronosd`; SIGSTOP of an agent or a whole node; proxy faults; workload crash storms. They run alongside user actions, with extended-resource requests whose names are generated per run (X-7).
  - A live checker samples the store and the OS process table every 200 ms (S1-S4, S11, S12), then checks liveness after the heal (L1, L2, L5). It writes `report.json` and `timeline.md`.
  - S3, S4 and S12 must hold in two consecutive samples, since the store and the process table can't be read atomically. A planted rogue process proves the checker sees violations on real processes.
- **CI:** 60 s of chaos and the B4 regression smoke on every PR; 3 × 10 min of chaos nightly, with the reports uploaded.
- **Benchmarks B1-B6** with raw samples in `bench/results/`, plots in `docs/img/`, and the write-up in `docs/BENCHMARKS.md`.

**What chaos found:**
1. **A metastable failure.** Agents gave up on a heartbeat after 160 ms (0.8 × the interval in the test timings). An overloaded `chronosd` missed that, because in full-sync mode its WAL fsyncs block the event loop. The agents fenced, restarted every workload at once (status and event writes, each one an fsync), and overloaded it again. One run never converged after the heal. **Fix:** the agent waits up to F/2 for a reply. That's safe because the lease counts from the *send* time, and a late reply is still evidence. The fsync on the event loop stays a known limitation.
2. **A false S12 in my checker.** It read units from `pod.status.assigned`, which lags: a fenced pod keeps its old units until it reports again. The runtime now puts each process's real units in `CHRONOS_ASSIGNED`, and the checker reads those.
3. **A guarantee's precondition not met.** At load 60-190 (three runs in parallel, plus macOS's Spotlight updater), S3 and S4 fired: shims fenced up to a second late. Fencing promises F + K + drift < E *in real time*; the test fixture's 0.2 s drift margin can't absorb that. **Fix:** chaos runs on the demo's timings (drift 1 s), the S4 bound includes the drift margin, seeds run one at a time as in CI, and reports record the load. After that: 3 × 10 min × 5 nodes all green, each with about 200 faults and actions and about 1 800 samples, converging 1.6-5.7 s after the heal.
4. **Harness bugs:**
   - Overlapping control-plane kills while a restart was still in progress.
   - A blocking `wait(timeout=5)` on the event loop.
   - Agents leaked by that same code path: three were found still running 3 hours later, and killed.
   - A cold `chronosd` start can exceed 15 s under load, so restarts now get 60 s and their duration is recorded.

**What the benchmarks found:**
- B4 showed 85% of scheduling time was deep-copying every cached Node on every decision. A read-only `Informer.view()` for hot paths made it 2.8-3.9× faster.
- B1 at R=100 measures process start-up, not the control plane: 100 Python shims start at once on 8 cores.
- B5 confirms macOS's plain fsync is nearly free (it doesn't reach stable storage); that's why the WAL uses `F_FULLFSYNC`.
- B6: snapshots keep recovery at about 0.2 s whatever the log length, against 124 s for 1M records without them.
