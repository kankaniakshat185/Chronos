# 2026-11-06: PM-2 (durability)

**Done:**
- `store/codec.py`: `[u32 length][u32 crc32][JSON {rev, op, kind, name, object}]`, little-endian; a frame decodes completely or is invalid.
- `store/wal.py`: segments `wal-<first rev>.log` (rotation, directory fsync); `durable_sync` (`F_FULLFSYNC` on macOS, fsync elsewhere); snapshots written as tmp → sync → rename → directory sync, keeping the newest two and deleting segments older than the older one.
- `recover()`: the newest snapshot with a valid CRC (falling back to the previous one), then contiguous records. An invalid frame at the end of the last segment with nothing intact after it is a torn write and is truncated; any other damage, or a revision gap, refuses to start. `repair=False` only reports.
- `common/crashpoint.py`: `CHRONOS_CRASHPOINT=<name>[:<nth>]` exits with 137. Points: `wal.before_write`, `wal.torn_write` (writes half a frame, then exits), `wal.before_fsync`, `wal.after_fsync_before_apply`, `segment.rotate`, `snapshot.before_rename`, `snapshot.after_rename_before_dirsync`.
- Store: every write goes through one path, log first and then `_apply_put`/`_apply_delete`, which recovery replays too. The pod-to-node index is maintained only inside apply, where before it was updated before the commit. A failed append raises `Unavailable` with memory untouched. `Store.open(data_dir)`.
- `chronosd run --data-dir` (default `~/.chronos/server`), `--no-wal-sync` (benchmarks only, warns loudly), `--snapshot-every`; it refuses to start on a corrupt log (exit 3). `chronosd wal-verify DIR`. Test clusters and the demo get their own server data dir; `restart_server()` keeps it.

**Not done here:** group commit (P6.2, optional in the plan) moved to PM-6, where benchmark B5 decides whether it's needed. A full fsync costs about 3 ms per write on this Mac (p50 2.97 ms, p99 3.44 ms), which is fine for one synchronous writer at Stage 1's scale.

**Tests:**
- Codec round trip.
- Recovery from **every byte truncation offset** of a 6-record log equals exactly the complete-record prefix, with the torn bytes removed.
- A bit flip in the last record is truncated; a bit flip anywhere before it refuses to start (100 random positions).
- A revision gap refuses to start; a failed log write (disk full) changes nothing.
- Reopening gives back exactly the same state after random writes with random snapshot intervals, and revisions continue from there (U2.3). Old segments are pruned; a damaged newest snapshot falls back; a leftover `.tmp` is ignored.
- **Durability harness (S8):** a seeded writer subprocess crashes at the nth hit of a crash point, where n is drawn from a crash-free calibration run of that seed, so every case really crashes. The recovered state must equal a reference run's state after the last finished write or after the in-flight one, and nothing else. **7 points × 50 seeds = 350 cases pass** (39 s with `-n auto`).
- **Control-plane restarts (U2.2, L4):** (a) `kill -9 chronosd` and back within F (3 s here): the same pods, PIDs and revision, no fencing, nodes still Ready past E. (b) Down longer than F: zero workload processes, then after the restart the same pods restart on their own nodes with new PIDs and nothing becomes NodeLost (startup grace, U2.1). (c) `kill -9` in the middle of a 0 → 20 scale-up: the scale survives and exactly 20 pods end up Running.
- All green on macOS (412 tests) and on Linux in Docker (412 tests, plus the 350-case durability run).

**Mutation checks:**
- Status writes that skip the log → 9 durability cases fail.
- Never truncating a torn tail → 5 cases fail.
- No startup grace → the long-outage test fails.
- Applying to memory *before* logging was **not** caught at first: after a process crash memory is gone either way, so the order only matters when the log write fails without a crash. Adding the disk-full test catches it.

**Caught along the way:**
- About 40% of the first harness runs never crashed, because my guessed hit counts were too high. Each seed's run is now calibrated first, and every case must exit with 137.
- The harness assumed one write per operation, but operation 0 made two (create the node, then mark it Ready). A crash between them gave a legitimate durable state the reference didn't list. Fixed by splitting it.
- `wal-verify` as first written would have truncated a torn tail while "verifying"; it now uses `recover(repair=False)`.
- With limitations removed, the README list would have rendered as 3, 4, 5, 7, …; renumbered.
