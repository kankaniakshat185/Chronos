# ADR-0024: Prometheus + Grafana for metrics and dashboards (required)

| Status | Date | Phase | Supersedes | Superseded by |
|--------|------|-------|------------|---------------|
| Accepted | 2026-11-06 | Stage 1, PM-5 (P7.4, P7.6) | — | — |

## 1. What
`chronosd` and every agent expose Prometheus metrics on `/metrics` using a fixed, golden-tested **metric catalog**. Stage 1 ships a **required** Prometheus + Grafana stack (Docker Compose, pinned images, provisioned from files) with a committed Chronos dashboard. It's tested in CI by an `observability-smoke` job. Metrics are for **observing** the system; benchmark numbers always come from raw samples.

## 2. Why
### Problem
Without metrics, the only way to see what Chronos is doing is `chronosctl get` and logs. That makes several things hard: spotting a slow reconcile loop, a growing work queue, heartbeat ages creeping up before an eviction, or fencing events during a chaos run. It's also a weak demo: watching a node fail and the cluster heal is far clearer on a live dashboard than in a refreshing table.
### Forces & constraints
- Prometheus + Grafana is the standard stack in the Kubernetes world, so it's familiar to reviewers and interviewers.
- Must not compromise measurement honesty: Prometheus data is bucketed and scrape-sampled.
- Must stay **scoped**: one dashboard, one compose file, no alerting.
- Docker isn't available on GitHub's macOS runners.
- The control plane must still never connect to agents (ADR-0010).

## 3. Alternatives considered
| Option | Pros | Cons | Verdict |
|--------|------|------|---------|
| **Chosen: Prometheus + Grafana, required, provisioned from files, CI-tested** | Standard; live dashboard; reproducible from the repo | Docker dependency for the stack; one more CI job | ✅ Chosen |
| A. `/metrics` only, no stack | Smallest | Nobody actually looks at raw `/metrics`; no demo value | ❌ |
| B. Prometheus + Grafana as an optional extra | No Docker dependency in the plan | Rots without a test; the demo depends on something unverified | ❌ (the user chose required) |
| C. TUI dashboard (Backlog P12.3) | No Docker | Custom code to maintain; not a standard tool | ⏸ Largely superseded |
| D. Full observability (Loki logs, Tempo traces, Alertmanager) | Complete | Far beyond scope | ❌ |
| E. Use Prometheus data for benchmarks | One data source | Histogram buckets and scrape sampling distort p99s and short events | ❌ |

**A** produces data nobody reads. **B** is how dashboards silently break; making it required means it's tested. **C** reinvents Grafana for one project. **D** is enterprise scope. **E** would undermine the benchmark methodology (TESTING.md §9).

## 4. How
### Components & files
```
deploy/observability/
├── docker-compose.yml            # prometheus + grafana, pinned image versions
├── prometheus.yml                # scrape_interval: 1s; file_sd_configs → targets.json
├── targets.json                  # generated by scripts/demo-cluster.sh and the test fixture
└── grafana/
    ├── provisioning/datasources/prometheus.yml
    ├── provisioning/dashboards/chronos.yml
    └── dashboards/chronos.json   # committed dashboard
src/chronos/common/metrics.py     # the metric catalog (single place where metrics are defined)
```
### Mechanism
- **Exposure:** `chronosd` serves `/metrics` on its API port. Each agent serves `/metrics` on `--metrics-port` with `prometheus_client.start_http_server`. Prometheus scrapes the agents; the control plane still never connects to them.
- **Targets:** `demo-cluster.sh` and the `cluster` test fixture write `targets.json` (file-based service discovery), so dynamic ports need no Prometheus restart.
- **Metric catalog** (defined only in `common/metrics.py`; names are an API):
  | Metric | Type | Labels | Source |
  |--------|------|--------|--------|
  | `chronos_nodes` | gauge | `condition` | chronosd |
  | `chronos_pods` | gauge | `phase` | chronosd |
  | `chronos_reconcile_duration_seconds` | histogram | `controller` | chronosd |
  | `chronos_workqueue_depth` | gauge | `controller` | chronosd |
  | `chronos_scheduling_duration_seconds` | histogram | — | chronosd |
  | `chronos_bind_conflicts_total` | counter | — | chronosd |
  | `chronos_unschedulable_pods` | gauge | `reason` | chronosd |
  | `chronos_node_heartbeat_age_seconds` | gauge | `node` | chronosd |
  | `chronos_resource_allocated` / `chronos_resource_capacity` | gauge | `node`, `resource` | chronosd (generic over resource names, X-1) |
  | `chronos_wal_fsync_duration_seconds` | histogram | — | chronosd (from PM-2) |
  | `chronos_agent_processes` | gauge | `state` | agent |
  | `chronos_agent_fence_events_total` | counter | — | agent (from PM-1) |
  | `chronos_agent_heartbeat_failures_total` | counter | — | agent |
- **Cardinality rule:** labels are bounded sets (conditions, phases, controller names, node names, resource names). **Never** pod names or UIDs.
- **Dashboard rows:** cluster overview · control loop · node health · resources · durability.
### Configuration
| Param | Default |
|-------|---------|
| Prometheus `scrape_interval` | 1 s (a 5 s eviction must be visible) |
| agent `--metrics-port` | assigned by the demo script / fixture |
| Grafana | anonymous viewer access on localhost only; admin password from env in compose |
### Edge cases & failure handling
- **Docker missing:** `make observability` fails with a clear message; Chronos itself runs normally. Only the stack needs Docker.
- **Agent killed:** its target goes `down`, which is itself visible on the dashboard as part of the node-failure story.
- **Metric renamed by accident:** the golden test fails.

### Implementation status (2026-11-06)
Implemented as designed: the catalog in `common/metrics.py` (all 14 metrics, golden-tested in `tests/golden/metrics.txt`), `GET /metrics` on `chronosd`, `--metrics-port`/`--metrics-host` on the agent (its own listener; the control plane still never connects to agents), `deploy/observability/` (Prometheus v2.55.1 and Grafana 11.3.1 pinned, 1 s scrapes, file service discovery, provisioned data source and dashboard, the dashboard as Grafana's home page), `make observability`, and the `observability-smoke` CI job. Details and deviations: cluster-state gauges (nodes, pods, unschedulable reasons, heartbeat age, allocated/capacity, queue depth) are computed from the store at scrape time by a collector, so they can't drift; counters and histograms are process-wide, in two registries so `chronosd` doesn't export the agent's counters as zeros. CPU is exported in cores (base units), memory in bytes. `_created` series are turned off. `chronos_unschedulable_pods{reason}` labels by each reason in the scheduler's message ("Insufficient cpu", "node NotReady"), which is bounded, never by the message itself. Reconcile and scheduling durations use the injected clock (virtual time in the simulator); the WAL fsync duration uses `clock.stopwatch()`. The dashboard is generated by `deploy/observability/grafana/build_dashboard.py`; a lint test checks every query uses only catalog metrics, every catalog metric has a panel, and the committed JSON matches the generator. The smoke test also runs every panel query against the live Prometheus. On macOS the containers reach the host through `host.docker.internal`; on Linux, `CHRONOS_BIND=0.0.0.0` (CI sets it). Verified locally on macOS (Docker Desktop): all targets up, 3 Ready nodes, NotReady visible after a node kill, dashboard provisioned, all panel queries valid. The Linux job runs in CI.

## 5. Consequences
**Positive:** a live, standard dashboard for debugging, chaos runs and demos; a catalog that's documented and tested.
**Negative / accepted costs:** Docker becomes a dev dependency for the stack; one more CI job (Ubuntu only).
**Risks & mitigations:** label-cardinality blow-ups → the cardinality rule plus a golden test of the label sets; the dashboard drifts from the metrics → dashboard lint.

## 6. Verification
- **Metric-catalog golden test** (T1/T4): `/metrics` from `chronosd` and an agent matches `tests/golden/metrics.txt` (names + label sets).
- **Dashboard lint** (T1): every panel query references only catalog metrics.
- **`observability-smoke`** (T4, Ubuntu CI): all targets `up`; `chronos_nodes{condition="Ready"} == 3`; kill a node → NotReady visible within 10 s; Grafana lists the provisioned dashboard.

## 7. Revisit when
Logs or traces become the debugging bottleneck (consider Loki/Tempo, which would need a new ADR), or the metric catalog needs per-pod data (rethink cardinality first).
